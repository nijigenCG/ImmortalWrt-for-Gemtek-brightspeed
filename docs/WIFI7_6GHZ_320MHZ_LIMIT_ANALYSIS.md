# Wi-Fi 7 6 GHz 320 MHz 实测极限分析：XR1710G Pure-AP 是否已触顶？

> 结论先行：在 **2×2 客户端 + 6 GHz 320 MHz + 单客户端 TCP** 这一消费级场景下，Phase J 的 **DL 3.42 Gbps / UL 2.73 Gbps** 已达到该链路物理层与 MAC 层效率的实际天花板，软件侧继续挖掘的空间很小（预计 < 5%）。

## 1. 本次实测基线

测试条件：Gemtek XR1710G (AN7581 + MT7996 + 10GbE) Pure-AP ↔ 一加 13 (2×2 Wi-Fi 7)，6 GHz ch37 / 320 MHz，近场 RSSI -7 ~ -9 dBm，有线对端 10GbE `iperf3`。

| 项目 | 实测值 |
| :--- | :--- |
| DL `P8`（IRQ 四核分流后） | **3,418.73 Mbps**（发送端 3,451.74） |
| UL `P8` | **2,700 ~ 2,726 Mbps**（`MCS12` 最高 69.1%） |
| 空口占用 `tx_air`（DL） | 约 80.2% |
| MPDU 重传率（DL） | 5.39% |
| 有线 10GbE 统计 | 累计 20.89 GB RX / 13.35 GB TX，0 error / 0 drop |
| `dmesg` | 全程零警告 |

## 2. 理论上限推算

2×2、320 MHz、GI 0.8 µs 的 EHT 物理层速率（每流 × 2 流）：

| MCS | 调制 / 码率 | PHY 速率 (2SS) |
| :--- | :--- | ---: |
| MCS 11 | 1024-QAM 5/6 | 约 3,843 Mbps |
| MCS 12 | 4096-QAM 3/4 | 约 4,323 Mbps |
| MCS 13 | 4096-QAM 5/6 | 约 4,803 Mbps（口径依标准表，部分资料引用 5,764 Mbps 为含 GI/条件的最大值） |

本次 DL 主导 MCS 为 `MCS11 ≈ 66%`、`MCS10 ≈ 18%`、`MCS12 ≈ 11%`，加权平均 PHY 约 3.9 ~ 4.0 Gbps；TCP 有效吞吐 3.42 Gbps 即 **约 85% 的 PHY 利用率**。

Wi-Fi 的 MAC 层开销（前导、IFS、BlockAck、A-MPDU 聚合边界、退避、TCP ACK 反向占空）使得单链路 TCP 吞吐通常只能达到 PHY 的 **80% ~ 90%**。因此：

- 在当前 MCS 分布下，3.42 Gbps 已处于该效率区间上沿；
- 要继续显著提升，只能靠**更高且稳定的 MCS**（需要更强的信道/EVM，即客户端与 AP 射频指标，而非软件）。

## 3. 本项目已验证的“软件侧可挖掘项”与结果

| 优化项 | 结果 | 结论 |
| :--- | :--- | :--- |
| `npu_tx_band_map=2`（5G+6G 走 PCIe0 Gen3 x2） | 峰值由约 2.4 提升到约 3.05 Gbps（Phase G） | 有效，已固化 |
| 6 GHz 关闭 eBF（避免 MT7996 固件锁死 MCS7） | 解除 MCS 锁死 | 有效，已固化 |
| mt76 / NPU / RRO 稳定性补丁（P0） | 重传与异常稳定性改善，无峰值跑分变化 | 稳定性收益 |
| IRQ 四核分流（中断原先全在 CPU0） | DL +356.8 Mbps（3,061.93 → 3,418.73），重传 6.33% → 5.39% | **有效，已固化到默认 `rc.local`** |
| `vow_atf=0` | 无净收益 | 弃用 |
| 降低发射功率 24 / 20 dBm | DL 下降 | 弃用 |
| `sku_power_ctrl=0` + 24 dBm | 重传上升 | 弃用 |
| MT7996 / Airoha NPU 固件 | 已是主线最新（MT7996 固件 202607；NPU 0.1111） | 无更新可用 |

最后一个有收益的优化（IRQ 分流）已经把 CPU 侧串行瓶颈消除；其后的各项控制变量实验均为零或负收益，说明剩余瓶颈不再在主机软件路径。

## 4. 与社区 / 评测资料的对照（定性）

以下为公开资料检索到的**大致范围**（不同来源测试环境差异大，仅作量级对照，未逐一复现）：

- 2×2 客户端在 6 GHz 320 MHz 下，理论链路速率常被引用为 **约 5.76 Gbps 量级**，但这是峰值 PHY 口径；
- 近距离、干净环境下，多家评测与社区反馈的 **TCP 实测多在 1.5 ~ 3+ Gbps**，个别极限场景可更高；
- OpenWrt + MT7996 / Banana Pi BPI-R4 类方案的社区 `iperf3` 结果多落在 **1.3 ~ 2.8 Gbps** 区间；
- 常见限制因素：客户端能力（是否真正协商到 320 MHz、2SS）、地区法规对 320 MHz 的限制、有线侧带宽（1G/2.5G 会直接封顶）、转发路径是否硬件卸载。

对照之下，本项目的 **3.42 Gbps DL** 位于公开可见结果的上沿，并且是在 **单客户端 TCP、10GbE 有线对端、硬件卸载（PPE/NPU）、AP CPU 约 1%** 的条件下取得。

> 说明：本节为定性对比，社区数字的测试条件（客户端型号、距离、协议、是否 UDP）不统一，不应视为严格的横向排名。

## 5. 为什么继续挖掘的空间很小

1. **物理层限制**：2×2 客户端的空间流上限为 2；MCS12/13 需要很高的 SNR/EVM，近场已大量命中 MCS11/12，再往上受客户端接收机与 AP 发射链路线性度约束。
2. **MAC 效率已接近上沿**：约 85% 的 PHY 利用率与约 80% 的空口占用，已处于 Wi-Fi 单链路常见效率区间。
3. **主机侧瓶颈已消除**：硬件卸载使 AP CPU 约 1%，IRQ 分流后无明显 CPU 串行点；PCIe0 Gen3 x2 (15.752 Gb/s) 对 3.4 Gbps 的单频负载有足够余量。
4. **固件生态已到上限**：MT7996 与 NPU 固件均为当前可获得的最新稳定版。
5. **多客户端 / MU 场景不同**：本测试为单客户端；若要进一步提升聚合吞吐，方向是多客户端 MU-MIMO / OFDMA，而非单链路峰值，属于不同的优化目标。

## 6. 仍可能带来增益的方向（预期收益有限）

| 方向 | 预期 | 备注 |
| :--- | :--- | :--- |
| 更强的 3×3 / 4×4 客户端 | 提升天花板 | 客户端侧条件，与 AP 软件无关 |
| 实验性 NPU 8.0 / 7.4-rc 内核（社区实验分支） | 未知，稳定性风险高 | 不建议作为主力基线 |
| 多客户端 MU / OFDMA 调优 | 提升总吞吐与公平性 | 需要多终端测试环境 |
| 更低噪声的部署环境 | 提升 MCS 分布 | 环境因素 |

## 7. 结论

- XR1710G Pure-AP（Phase J + IRQ 分流）在单客户端 6 GHz 320 MHz 场景下已接近该链路的实际上限；
- 已完成的有效优化项均已固化（`npu_tx_band_map=2`、6G eBF 关闭、IRQ 分流），其余尝试均为零或负收益；
- 后续工作建议转向**长期稳定性验证**与**多客户端场景**，而不是继续压榨单链路峰值。
